# Сервер заказов MenuLive

HTTP API и поток событий для гостевого меню и приложения официанта.
Контракт: [`docs/api-orders.md`](../docs/api-orders.md). Он единственный источник правды,
этот файл только объясняет, как запустить и обслуживать сервер.

## Что внутри

- Ноль внешних зависимостей. Только встроенные модули Node: `node:http`, `node:fs`,
  `node:crypto`, `node:path`, `node:url`. Обновление на сервере это `git pull` плюс
  перезапуск сервиса, никакого `npm install`.
- Node 20+, ESM.
- События через SSE, не через WebSocket.
- Хранилище: JSON-файлы в `server/data/`. Запись атомарная: временный файл рядом,
  затем `fs.renameSync`.
- Цены и названия блюд берутся только из `restaurants/<id>.json`. Файл перечитывается,
  когда меняется mtime или размер. Цены, присланные клиентом, игнорируются.

## Структура

```
server/
  index.js             точка входа, роутинг, запуск, проверка токена
  lib/http.js          разбор тела, JSON-ответы, ошибки по контракту, CORS, валидаторы
  lib/store.js         чтение и запись JSON с атомарной заменой
  lib/menu.js          конфиг ресторана: цены, названия, языки, сервисный сбор
  lib/orders.js        заказы: идемпотентность, статусы, номера, справочник официантов
  lib/calls.js         вызовы официанта и просьба счёта
  lib/sse.js           хаб подписок, буфер последних 500 событий, ping раз в 25 секунд
  test/run.js          прогон: поднимает сервер на случайном порту и проверяет API
  data.example/        примеры файлов хранилища, их кладём в репозиторий
  data/                боевые данные, в репозиторий не попадают (.gitignore)
```

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|------------|--------------|-------|
| `MENULIVE_STAFF_TOKEN` | нет | Токен персонала для заголовка `X-Staff-Token`. Без него все методы персонала отвечают `401`. В коде и в репозитории токена нет. |
| `PORT` | `4010` | Порт. |
| `HOST` | `127.0.0.1` | Адрес. Наружу отдаёт nginx, менять не нужно. |
| `MENULIVE_DATA_DIR` | `server/data` | Где лежат JSON-файлы хранилища. |
| `MENULIVE_RESTAURANTS_DIR` | `<репозиторий>/restaurants` | Где лежат конфиги ресторанов. |
| `MENULIVE_TZ_OFFSET` | `300` | Смещение локального времени в минутах (Ташкент, UTC+5). По нему считается граница суток для сброса дневного счётчика номеров. |

## Файлы хранилища

- `orders.json` - заказы. Держим 30 дней и не больше 5000 штук, старое отрезается при записи.
- `calls.json` - вызовы официанта, те же ограничения.
- `seq.json` - счётчики человеческих номеров по ресторанам.
- `staff.json` - справочник сотрудников. Правится руками, сервер перечитывает его при
  изменении. По полю `by` из запроса смены статуса отсюда подставляются `waiter.name`
  и `waiter.initials`. **Токенов в этом файле нет**: токен только в окружении.

```json
{
  "staff": [
    { "id": "aziz", "name": "Азиз Каримов", "initials": "АК", "restaurant": "brest" }
  ]
}
```

Если сотрудника нет в справочнике, гость увидит логин из поля `by` и инициалы из него.

## Номера заказов

Человеческий номер это буква, дефис и счётчик: `А-1204`. Счётчик сбрасывается каждые
сутки по локальному времени (`MENULIVE_TZ_OFFSET`), буква при этом берётся следующая,
чтобы вчерашние и сегодняшние номера не путались. Алфавит без похожих на цифры букв:
`АБВГДЕЖИКЛМНПРСТУФЦЧШЭЮЯ`. После 9999 заказов за сутки счётчик начинается заново,
а буква сдвигается.

## Локальный запуск

```bash
cd server

# Windows PowerShell
$env:MENULIVE_STAFF_TOKEN = "любой-длинный-секрет"
node index.js

# Linux, macOS, Git Bash
MENULIVE_STAFF_TOKEN="любой-длинный-секрет" node index.js
```

Проверка:

```bash
curl http://127.0.0.1:4010/api/v1/health

curl -X POST http://127.0.0.1:4010/api/v1/orders \
  -H 'Content-Type: application/json' \
  -d '{"restaurant":"brest","table":"12","clientOrderId":"c_demo1","items":[{"dishId":"plato","qty":1}]}'

curl -N -H "X-Staff-Token: любой-длинный-секрет" \
  'http://127.0.0.1:4010/api/v1/stream?restaurant=brest&role=waiter'
```

Путь можно писать и как `/api/v1/orders`, и как `/v1/orders`, и как `/orders`:
сервер сам отрезает префикс, чтобы роутинг не зависел от настроек прокси.

## Тесты

```bash
node server/test/run.js
# или
cd server && npm test
```

Прогон поднимает сервер на случайном порту, кладёт данные во временную папку и
проверяет: расчёт денег по конфигу ресторана, идемпотентность `clientOrderId`,
запрет прыжка через шаг в цепочке статусов, `401` без токена и с чужим токеном,
доставку событий в SSE (включая добор по `Last-Event-ID` и фильтрацию для гостя),
вызовы официанта и целостность файлов на диске. Внешних зависимостей у теста нет.

## Деплой на сервер

Один раз:

```bash
# 1. Файл с секретами, в репозитории его нет
sudo install -m 600 -o root -g root /dev/null /etc/menulive-orders.env
sudo tee /etc/menulive-orders.env >/dev/null <<'EOF'
MENULIVE_STAFF_TOKEN=сюда-длинный-случайный-секрет
PORT=4010
EOF

# 2. Папка данных, писать в неё должен www-data
sudo mkdir -p /var/www/ar-menu/server/data
sudo cp -n /var/www/ar-menu/server/data.example/*.json /var/www/ar-menu/server/data/
sudo chown -R www-data:www-data /var/www/ar-menu/server/data

# 3. Сервис
sudo ln -sf /var/www/ar-menu/deploy/menulive-orders.service /etc/systemd/system/menulive-orders.service
sudo systemctl daemon-reload
sudo systemctl enable --now menulive-orders

# 4. nginx (конфиг уже лежит в репозитории по симлинку)
sudo nginx -t && sudo systemctl reload nginx
```

Каждое обновление:

```bash
cd /var/www/ar-menu
git pull origin main
sudo systemctl restart menulive-orders
journalctl -u menulive-orders -n 50 --no-pager
```

Токен для приложения официанта генерируется так:

```bash
openssl rand -hex 32
```

## Решения, которые контракт оставил открытыми

- **Токен персонала.** Контракт упоминает `server/data/staff.json` как место хранения
  токена. По требованию безопасности токен читается только из `MENULIVE_STAFF_TOKEN`,
  а `staff.json` остался справочником имён и инициалов. Сравнение токена
  через `crypto.timingSafeEqual`.
- **Сервисный сбор.** 10 процентов, как в примере контракта. Значение можно
  переопределить в конфиге ресторана полем `"service": 12` или `"service": { "percent": 12 }`.
- **Повтор того же статуса.** `POST /orders/:id/status` с текущим статусом возвращает
  `200` и заказ без изменений, событие не шлётся. Это не прыжок через шаг, а повтор
  запроса при плохой связи.
- **Откат из `cancelled`.** Разрешён только в тот статус, который был до отмены
  (берётся из `timeline`). Вперёд из `cancelled` нельзя, ответ `409`.
- **Повтор вызова официанта.** Тот же вызов возвращается, пока не закрыт вызов того же
  вида (`waiter` или `bill`) с того же стола. Просьба счёта и вызов официанта это
  разные вызовы.
- **`GET /calls?restaurant=brest&open=1`** добавлен сверх контракта: официанту нужен
  список открытых вызовов после переподключения, так же как `GET /orders` для заказов.
  Метод персонала, нужен `X-Staff-Token`.
- **Поток для гостя** принимает `orderId`, либо `table`, либо оба. Если передан только
  `orderId`, стол берётся из заказа.
- **`Last-Event-ID`** читается из заголовка, а если его нет, из query-параметра
  `lastEventId`. Буфер 500 событий живёт в памяти и обнуляется при перезапуске сервиса,
  поэтому официант после обрыва всё равно делает `GET /orders`, как требует контракт.
